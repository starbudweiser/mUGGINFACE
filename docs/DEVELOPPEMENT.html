1. Vue d'ensemble

Application macOS native, Swift 5 / SwiftUI, cible arm64-apple-macos15, sans dépendance externe ni gestionnaire de paquets : tous les fichiers de Sources/ sont compilés d'un coup par swiftc (build_app.sh). Réseau : URLSession seul. Stockage : fichiers JSON dans Application Support, UserDefaults pour les préférences, Trousseau pour les jetons. Design : Flat Mat clair / sombre (Theme.swift). 4 langues, mêmes clés partout (L10n.swift, L10nAudit.swift).

4. Flux

Lancement → Hardware.detect → lecture catalog.json (affichage immédiat) → startScheduler (minuterie 10 min)
  scan() : pour chaque domaine → Hub.fetch (tendance + téléchargements, 40 chacun) → fusion dans models
         → top 10 par domaine vs snapshot → WatchEvent (new / enter / rise / removed) → save() + notification
         → refineWeights (taille réelle, 150 modèles max, 4 requêtes en parallèle)
         → si Prefs.auditAuto : AuditStore.run(auto: true)

5. Algorithmes

5.1 Poids, RAM, adéquation (Scoring)

  • Poids = paramètres × bits / 8 × 1,05 (paramètres : nom du dépôt, sinon safetensors / GGUF ; bits : nom et étiquettes, table des quantifications). Remplacé par realGB (somme réelle des fichiers de référence) après refineWeights.
  • RAM = poids × 1,10 + 1,5 Go. Utilisable = mémoire totale − réserve (défaut 16 Go). Niveaux : ≤ 60 % Fluide, ≤ 85 % Compatible, ≤ 100 % Limite, sinon Trop lourd.
  • Débit (LLM) = min(400, bande passante × 0,7 / poids).

5.2 Performance et score

performance = 10 × (0,30 taille + 0,28 j'aime + 0,22 téléchargements + 0,10 tendance + 0,10 fraîcheur), chaque terme borné à [0, 1] (échelles logarithmiques pour taille, j'aime, téléchargements ; fraîcheur linéaire sur 365 jours). Score = 0,62 × performance + 0,38 × légèreté (1 − RAM / utilisable).

Piège rencontré : dans le cache Hub, les fichiers de snapshots/ sont des liens vers un dossier blobs/ partagé. Mesurer le dossier du modèle donne ≈ 0. linkedSize résout chaque lien et dédoublonne les chemins résolus.

6.2 Identification et domaine

  1. AuditStore.match : identifiant exact, puis insensible à la casse, puis même baseName (suffixes de quantification retirés : 4bit, 8bit, bf16, fp16, mlx, gguf, q4…), en gardant le plus aimé.
  2. Si l'identifiant ressemble à un dépôt Hub : Hub.info (une requête avec expand[]=pipeline_tag,evalResults,…, mise en cache mémoire) donne domaine, métadonnées et benchmarks.
  3. Sinon guessDomain (mots du nom) ; sinon « Hors catalogue ».

6.3 Candidat et verdict

  • Candidats = AppModel.rows(domains:[d], filtered:false) filtrés : adéquation ≠ Trop lourd ; pas le même modèle ni la même famille (baseName) ; ni mots parasites (uncensored, abliterated, heretic, jailbreak, nsfw, unfiltered) ; ≥ 100 j'aime ; même tâche (étiquettes de pipeline, avec regroupements embeddings et vidéo) ; pas de sous-tâche voisine (diariz, segmentation, vad, pii, punctuation) absente du modèle installé.
  • Meilleur = performance maximale. gain = perf(meilleur) / perf(installé) − 1. Verdict : ≥ 0,15 → Mieux disponible, sinon À jour ; Hors catalogue si aucune donnée.
  • Benchmarks : commonEval = premier couple (dataset, tâche) présent dans les deux fiches ; valeurs affichées côte à côte sans jugement de sens (certaines métriques baissent en s'améliorant, ex. WER).

6.4 Indice et instantanés

Indice = moyenne sur les modèles connus de min(1, perf / max(perf, perf du candidat)) × 100. Un instantané par jour (Calendar.isDate(inSameDayAs:) : le dernier remplace le précédent), 120 conservés. changes compare les identifiants du dernier et de l'avant-dernier instantané. Déclenchement : bouton, .task à l'ouverture si la liste est vide, fin de scan() si auditAuto et dernier audit > 20 h.

6.5 Interface (AuditView)

  • Trois cartes de résumé de même largeur et même hauteur (HStack.fixedSize(vertical) + maxHeight: .infinity), carte Évolution, une carte par domaine, carte Dossiers.
  • Règle d'alignement : le cadre (frame) se pose avant .card() pour que le fond de la carte prenne toute la largeur ; colonnes de ligne à largeurs fixes (source 140, taille 64, score 104, verdict 120, nom flexible) pour que tout s'aligne d'une ligne à l'autre.

6.6 Analyse et mise à jour assistées (AuditAgent.swift)

AuditAgentStore (singleton principal) pilote l'agent via AgentBridge.run, étendu avec extraRules (règles d'autorisation Claude Code), addDirs (--add-dir) et timeout (garde-fou qui termine un agent bloqué).

ÉtapeFonctionDétail
Analyseanalyze()Invite en anglais avec les données d'audit (aucune donnée personnelle) ; réponse dans la langue de l'application ; stockée dans audit-agent.json. Sans outils, délai 5 min.
PlanpreparePlan()Remplacements cochés + fichiers d'instructions + règles imposées au plan ; texte éditable (draftPlan). Sans outils.
SauvegardemakeBackups(id)Copie chaque fichier / dossier d'instructions et le journal WORKFLOW-EVOLUTION.md dans plans/<id>/backup/<n>-nom ; backup = nil si le fichier n'existait pas (sera retiré au retour).
Exécutionexecute()Crée journal.json vide, enregistre le plan (statut Préparé), lance l'agent avec outils : règles Edit(//chemin) (et /** pour un dossier) pour les seuls fichiers autorisés, journal et dossier du plan en --add-dir, délai 45 min. Statut Exécuté ou Échec ; téléchargements lus dans le journal.
Retourrollback(id)Restaure chaque sauvegarde (le fichier courant part dans replaced/), retire ce que le plan a créé, met à la corbeille (trashItem) les téléchargements du journal. Chemins validés : fichiers = liste d'instructions + journal ; modèles = dossier des modèles, cache Hub, dossiers analysés.
Le journal écrit par l'agent est une donnée non fiable : l'application ne s'y fie que pour des chemins situés dans des racines autorisées, et jamais pour supprimer définitivement (corbeille seulement).
Pièges rencontrés : la règle Write(...) est refusée par Claude Code (Edit couvre toute écriture de fichier) ; les chemins absolus des règles s'écrivent avec // au début ; un agent sans délai maximal peut bloquer l'interface. Test de bout en bout réalisé (agent réel, dossiers temporaires, bundle d'essai séparé) : exécution, fichier modifié, journal créé, retour arrière complet.

7. Réseau

  • Liste : GET /api/models?pipeline_tag=…&sort=trendingScore|downloads&limit=40&expand[]=downloads,likes,lastModified,createdAt,tags,gated,safetensors,trendingScore,gguf.
  • Fiche : GET /api/models/{id}?expand[]=…,pipeline_tag,evalResults. Fichiers : /api/models/{id}/tree/main?recursive=true.
  • User-Agent générique « mUGGINFACE », jeton Trousseau en Bearer si présent. Aucune donnée personnelle.

8. Internationalisation

Table par langue dans L10n.swift, fusionnée avec auditFr / En / Es / It (L.tables). L.t(clé, arguments…) retombe sur l'anglais puis sur la clé. Toute nouvelle chaîne s'ajoute dans les 4 langues, avec les mêmes clés.

9. Construction, signature, installation

cd mUGGINFACE
DEV=1 NO_OPEN=1 ./build_app.sh      # « mUGGINFACE dev.app » (fr.stephan.mugginface.dev, données séparées), signée, non installée
./build_app.sh                      # version installée dans ~/Applications/Applications Personnelles (signature locale stable)
open -g -j "mUGGINFACE dev.app"     # lancement sans prendre le focus

Le script compile Sources/*.swift (-O -swift-version 5 -parse-as-library), copie l'icône et les InfoPlist.strings des 4 langues, signe avec /Volumes/SKYRIM/TOOLS/MAC/_tools/sign_app.sh. Les données de la version dev sont séparées (dossier Application Support au nom de son identifiant).

10. Marche de développement et de publication

  1. Modifier, compiler en dev, tester (lancement en arrière-plan, captures par screencapture -l <id de fenêtre>).
  2. Mettre à jour la version locale installée avec ./build_app.sh ; quitter (⌘Q) puis relancer l'appli pour voir la nouvelle version.
  3. Pas de notarisation, de push ni de release à chaque retouche. Sur demande « compile, notarise et pousse » : tests, release.sh (notarisation par _tools/notarize_app.sh, profil « Applications »), commit et push sur main.

11. Ajouter une fonction : liste de contrôle

  • Maquette dans le design de l'appli (voir le PDF de maquettage), validée avant le code.
  • Textes dans les 4 langues, aucune chaîne visible en dur.
  • Alignements vérifiés (cartes de même largeur, colonnes fixes) en clair et en sombre.
  • Aucune donnée personnelle dans les requêtes ; un nom d'appli dans l'interface garde le « m » coloré, sauf dans un menu déroulant.
  • Test en dev (arrière-plan), puis version locale installée, puis seulement à la demande notarisation et publication.

12. Pistes

  • Banc d'essai local par domaine (vitesse mesurée, qualité sur un jeu d'exemples) pour compléter l'indice estimé.
  • Source de classements publics supplémentaires (MTEB, Open ASR, Artificial Analysis) si une API stable existe.
  • Ranking moins sensible à la popularité (filtre des variantes bricolées dans toute l'appli, pas seulement dans l'audit).
  • Export de l'historique d'audit (CSV) pour suivre l'atelier dans un tableur.
